# Beautiful Tooltip

## 定位

产品经理把模糊需求交给前端，前端用本 skill 把 tooltip 一次做对，产出**一份可直接发给产品经理确认的单文件 HTML**。产品经理不必再自己写 tooltip 文案和排版——文案由本 skill 从功能逻辑里推导出来。

**本 skill 不规定组件化程度**：用共享组件、还是每个页面各写一份样式，由前端按项目情况决定。本 skill 只规定四件事——外观怎么统一、交互怎么统一、文案怎么写、交付什么。

## 工作流

1. **找全锚点**：读需求/PRD/设计稿/现有代码，列出这一屏**所有**需要提示的交互点（按钮、图标、字段、状态、表格单元格、图表数据点、禁用项）。漏一个，用户就多一次困惑。
2. **判断类型**：对每个锚点判断内容属于哪一类 → 定宽度、定对齐、定箭头位置（第一部分）。
3. **写文案**：主动读功能逻辑，替用户问出「这是什么 / 为什么不能点 / 点了会怎样」→ 写出答案（第二部分）。
4. **生成预览**：产出自包含的单文件 HTML，产品经理双击能看、直接能改（第三部分）。
5. **确认后落地**：产品经理在 HTML 上改完文案确认，前端把结构、文案、尺寸映射进代码。

## 第一部分：统一设计语言与交互规范

这一部分是硬约束。同一产品里所有 tooltip 必须共用同一套尺寸、圆角、间距、动效和定位策略——用户不该在两个页面看到两种气泡。

### 1.1 宽度：默认固定，只有一种情况自适应

| 情况 | 宽度 | 判据 |
|---|---|---|
| **默认** | 固定 300px（需要更宽/更窄时从 240 / 300 / 360 三档里选） | 两行及以上；含结构（标签、进度条、图表、步骤、键帽）；含按钮/菜单/链接；含运行时变量（文件名、人名、计数、百分比）；同一列表/表格里重复出现 |
| **例外** | 自适应 160–300px（`fit-content`） | **单行、≤12 字、无结构、无图标、无按钮** |

**为什么默认固定**：tooltip 是覆盖层，宽度跳动会让眼睛重新定位；按钮的点击区域更不能随文案长短漂移——用户第二次来找同一个按钮会点空。含运行时变量的内容尤其不能自适应，数据一变宽度就跳。

**为什么留自适应**：固定 300px 装 8 个字，六成是空白，看着像布局出错；而且越窄遮挡越少。

判据一句话：**最长一行 ≤12 字且只有一行 → 自适应；否则固定。** 固定宽度也要保留 `max-width: 100%` 以适配窄屏。

### 1.2 对齐：一句居中，一段居左

| 情况 | 对齐 | 理由 |
|---|---|---|
| **单行、无结构、无图标的纯文本** | 居中 | 内容比最小宽度还短时，居左会在右侧留出难看的空白 |
| **两行及以上** | 居左 | 左边缘是一条稳定的线，眼睛不用每行重新找起点；居中会让每行参差 |
| **带图标/头像** | 居左 | 图标锚定左边缘，居中会破坏图标与文字的从属关系 |
| **列表、步骤、键帽、标签行** | 居左 | 结构性内容必须居左 |
| **含按钮/操作** | 居左 | 操作区与文字共享左边缘 |
| **数值/数据** | 居左（或右对齐） | 绝不居中 |

判据：内容是一「句」还是一「段」？一句 → 居中；一段或一列 → 居左。带图标或按钮 → 一律居左。

### 1.3 箭头：默认居中，只在必要时偏移

**命名语义（先看这条，避免搞反）**：`.a-top-*` 指**箭头在 tooltip 的上边**（箭头朝上 → tooltip 在锚点下方，等价于标准 UI 库的 `placement=bottom`）；`.a-bottom-*` 指箭头在 tooltip 的下边（箭头朝下 → tooltip 在锚点上方，等价于 `placement=top`）。

**总原则**：箭头唯一的作用是「指认归属」——让用户一眼看出这个浮层属于哪个元素。所以默认策略永远是**箭头对准锚点中心**，偏移只是空间不够时的妥协。

- **默认：tooltip 在锚点上方，箭头下边居中（`.a-bottom-center`）**。绝大多数场景。
- **翻转：tooltip 在锚点下方，箭头上边居中（`.a-top-center`）**。锚点靠近视口/容器顶部、上方放不下时自动翻转——这是算法行为，不是人工选择。
- **偏移到起始 / 末尾**（同一侧的三个位置），满足任一条：
  1. 锚点靠近视口边缘（工具栏最右一个图标）；
  2. 锚点比 tooltip 窄很多且贴边；
  3. 锚点是表格/列表里的某一列单元格——箭头要对准该列的横向中心，而不是整行中心；
  4. tooltip 会盖住用户正要看的相邻内容。
- **左右两侧**：锚点在垂直工具栏/侧边栏、或上下都放不下、或上下方向会盖住用户正在读的内容时使用。
- 偏移量下限：距圆角 14px，避免箭头压在圆角上。

12 种类名与完整定位逻辑见 `reference/design-spec.md`。

### 1.4 量化红线

| 项 | 上限 | 备注 |
|---|---|---|
| 短句 | **≤12 字** | 同时是**自适应宽度的判据**和**居中判据**——三个判据合成一条 |
| 说明段 | **≤3 行** | 超过就精简，或改用可交互浮层 |
| 标签 | ≤3 个 | 超过换行或删 |
| 按钮 | ≤2 个 | 主操作在右，危险操作单独用红 |
| 列表项 | ≤5 条 | 超过改用页面内说明 |

### 1.5 交互时序

| 行为 | 规则 |
|---|---|
| 鼠标悬停出现 | 延迟 **400ms**——鼠标只是划过时不该闪出提示 |
| 鼠标移开消失 | 延迟 **150ms**——留出把鼠标移进 tooltip 的时间 |
| 键盘 focus | **立即**出现，不等 400ms |
| Esc | 关闭当前 tooltip |
| 触屏 | **点按切换**显示/隐藏（触屏没有 hover） |
| 默认位置 | tooltip 在锚点**上方**（`.a-bottom-center`），空间不足自动翻转 |

### 1.6 尺寸、颜色、动效、无障碍

- 圆角 14px；内边距 14px 16px；箭头 8px；tooltip 与锚点间距 8px。
- 层级：tooltip 在最上层，且不遮挡锚点本身。
- 主题色走 `--accent` 令牌，语义色（成功绿、警示红、状态点）**不随主题色变化**——红色警告不能被主题色带偏。
- 深浅色跟随系统；深色底用中性灰，不要偏蓝。
- 动效 150–200ms 淡入 + 轻微位移，不做弹跳，尊重 `prefers-reduced-motion`。
- 无障碍：`role="tooltip"` + `aria-describedby`；键盘 focus 也能触发。
- **可交互内容要保证鼠标能移进去**（锚点与 tooltip 之间无间隙或延迟消失），否则按钮点不到。若必须长时间停留，说明它本质是 popover 而非 tooltip，交互方式要另议。

### 1.7 明确不要做的

- 不要在 tooltip 里塞必须点击才能完成的关键操作——鼠标一移开就消失。
- 不要用 tooltip 承载长文、帮助文档、免责声明。
- 不要给同一个元素挂多个 tooltip。
- 不要用 tooltip 代替表单校验错误提示（错误要常驻在字段旁）。

## 第二部分：文案生成规范

这一部分替代产品经理写 tooltip 文案和排版的工作。**先读功能，再写文案**——不要照着元素名称复述。

### 2.1 三步法

1. **读功能**：这个元素是什么？点了会怎样？数据从哪来？为什么可能不能点？读代码、读接口、读设计稿，把答案弄清楚。
2. **找疑问**：用户此刻悬停在这里，心里在问什么？「这是什么」「为什么是灰的」「点了会不会删掉」「这个数字怎么算的」。
3. **写答案**：文案只回答那个疑问，不复述元素名称，不写元描述。

### 2.2 措辞规则

- 一句话说清「是什么 + 会怎样」；能用一句不用两句。
- 用用户的词，不用系统的词：「保存」不是「提交持久化」，「3 个文件」不是「3 个实体」。
- 动词开头、主动语态：写「复制链接」，不写「点击这里可以复制链接」。
- 数字带单位和上下文：`4.2 MB · PDF · 修改于 2 天前`，不是 `大小 4.2`。
- 危险操作说清后果和不可逆性：「删除后不可恢复，该文档及其 12 条评论将被永久删除」。
- 受限操作说清「为什么不能」和「怎么办」：「你可以查看和评论，但不能编辑。如需编辑权限，请联系空间管理员」。
- 空状态说清「为什么空」和「下一步」：「本周还没有新工单。创建第一个工单后，这里会显示趋势与负责人分布」。
- 进度类给总量和剩余时间，不只给百分比：「已同步 3,142 / 5,068 个文件」。
- 长度上限：标题 ≤14 字；正文每行 ≤ 约 20 字、最多 3 行。超了要么精简，要么改用可交互浮层。
- 不用感叹号，不用「请注意」，不写「这是一个提示」这类元描述。

### 2.3 排版

- 标题 + 正文：标题给结论，正文给补充。
- 标签 ≤3 个，超过就换行或删。
- 按钮 ≤2 个，主操作在右，危险操作单独用红色。
- 数据类：大数字 + 单位 + 环比 + 时间范围。

22 个可直接套用的内容原型（含适用场景与示例文案）见 `reference/copywriting.md`。

## 第三部分：交付物规范

### 3.1 产出什么

一个**自包含的单文件 HTML**（无外部依赖、无网络请求、双击即看），发给产品经理确认。命名 `tooltip-<功能名>-预览.html`。

必须包含：

- 顶部一段说明：这是什么需求、要确认什么、哪些地方需要产品经理拍板。
- 每个 tooltip 配一个真实的锚点元素（按钮/图标/文字），**能真实悬停**，不要只摆一排气泡。
- 真实业务文案，不要 Lorem，不要「示例文本」。
- 深浅色两种底色的效果（跟随系统即可）。
- 你这次要交付的全部 tooltip 状态。

### 3.2 让产品经理改得动

- 文案集中放：能用一个 JS 数组或显眼的 HTML 区块管理最好，产品经理改字不用懂代码。
- 每个 tooltip 旁标注它的类型（自适应/固定、箭头位置），方便对话。
- 不要在预览里放实现细节（构建产物、框架代码）——产品经理看不懂，只会增加沟通成本。

### 3.3 确认之后

- 产品经理直接在 HTML 上改文案 → 确认 → 前端把结构、文案、尺寸映射进代码。
- 这个 HTML 是沟通产物，**不要提交到主分支**。
- 落地时宽度、对齐、箭头规则照旧执行，不要因为"反正产品经理确认的是这个 HTML"就照抄预览里的临时写法。

## 检查清单

交付前逐条过：

- [ ] 这一屏所有需要提示的交互点都覆盖了？
- [ ] 每条 tooltip 的宽度选择符合 1.1 的判据？
- [ ] 对齐符合 1.2？
- [ ] 箭头位置默认居中，偏移的每一条都有理由？
- [ ] 文案回答了用户真实的疑问，而不是复述元素名称？
- [ ] 数字带单位、危险操作说清后果？
- [ ] 深浅色都看过？
- [ ] 键盘 Tab 也能触发？
- [ ] HTML 是自包含的、产品经理能直接改文案？

## 用出经验就回写本 skill

用本 skill 的过程中如果发现更好的做法——规则有漏洞、文案原型不够用、宽度/箭头判据有例外、踩到新的坑——**不要只在本地绕过去**：

1. **先把当前任务按正确做法做完**，不要卡在规范上。
2. 把经验沉淀成对 skill 的改动：改 `SKILL.md` 或对应的 `reference/` 文件，在改动处说明「改了什么、为什么」。
3. **提交 PR 到本 skill 的仓库**（superteam-pack 的 git 仓库），标题写清触发场景，正文附上真实案例。
4. 在 `session-memory.md` 追加一条记录：日期 + 场景 + 改动 + 原因。

这样下一个用它的人拿到的是改好的版本，而不是把同一个坑再踩一遍。
